# A rail is an adapter, not a schema

That sentence is in the brief and in the T+2h attack plan. This document is
about making it true of the code.

`src/lib/rails/contract.ts` is the contract. `src/lib/rails/adapters/` is the
five adapters. `src/lib/rails/contract.test.ts` is the argument that the
abstraction earns its keep — and if you only read one thing here, read the
capability table in §3, because it is generated from the adapters and it says
more about this system's honesty than any paragraph.

---

## 1. What the interface was

It was **two** interfaces and **three** modules behind neither.

| Module | Behind an interface? |
|---|---|
| `increase/` | `PaymentRail` |
| `achsim/` | `PaymentRail` |
| `stablecoin/` (direct signing) | `StablecoinPayoutProvider` |
| `stablecoin/` (Circle) | `StablecoinPayoutProvider` |
| `lithic/` | **no** — a module of free functions |
| `plaid/` | **no** — a module of free functions, and correctly so |

`PaymentRail` — `initiateCredit`, `initiateDebit`, `getTransfer`, `parseEvent` —
is a good interface and it had **two implementations, both of them ACH**. One
rail, twice. `types.test.ts` held two stub rails, a card one and a USDC one,
that existed to be type-checked and were never implemented, so the claim "card
and USDC fit behind these four methods" was a compile-time claim about
hypothetical code.

`StablecoinPayoutProvider` — `id`, `label`, `health()`, `send()` — is the one
that was genuinely polymorphic: two real providers, one ledger posting, an
outcome union nobody can smuggle an acknowledgement through. It is the model
this contract follows.

The two interfaces disagreed about the same ideas:

- **Identity** was `RailCapabilities` in one and `{ id, label }` in the other,
  and nothing at all for Lithic or Plaid.
- **Liveness** was spelled four ways in the repo: `ProviderHealth.liveness`
  (four words), `ProbeResult.liveness` in `src/lib/integrations/probe.ts` (six),
  `RailSlotHealth` (no liveness at all — it reports which adapter was
  *selected*), and, inside `rails/`, nothing for the card or open-banking slots.
- **The seven-member `RailEvent` union** was used by nothing outside
  `src/lib/rails/`. The card rail's events reached the ledger as raw Lithic
  `Transaction` objects through `src/lib/holds/`.

So the directory was one polymorphic rail, one rail implemented twice, and two
clients with ad-hoc callers.

## 2. The five operations, named from the evidence

Not from a textbook. From what these five modules actually do:

| Operation | What it means | How many rails |
|---|---|---|
| `originate` | push an instruction onto the network | 3 of 5 |
| `observe` | turn a verified inbound delivery into a normalised fact about money | 3 of 5 |
| `settle` | report that money finally moved, and for how much | 3 of 5 |
| `reverse` | report that settled money came back | 2 of 5 |
| `probe` | describe its own liveness | **5 of 5** |

**`probe` is the only universal one.** That is the finding, not a
disappointment. "Is this integration live, and is what it produces evidence of
anything" is asked of every slot, on every health surface, in the README table,
and by the one rule in this trial that fails a submission outright — and it had
five implementations and no interface.

### Unsupported is a type, not a throw

An adapter that throws "not supported" at runtime is a schema pretending to be
an adapter. So an unsupported operation is expressed twice, and neither is a
runtime failure:

1. **The method is absent from the type.** `canObserve(rail)` and
   `canOriginate(rail)` narrow. Calling `observe` on a rail that does not have
   one is a compile error, not a `RailError` at 3am.
2. **`supports[operation]` carries the reason**, in domain terms, machine
   readable — which is what makes §3 generated rather than typed.

### And a supported operation carries its proof

"Never claim a capability not proven by a real call." `RailSupportEntry` makes
that a field:

- `measured` — exercised against the provider's own system, sandbox included.
- `simulated` — exercised, but only against our simulator.
- `unexercised` — real code, wire shape from documentation, never once run
  against the provider.

## 3. The capability matrix

**Generated from the adapters.** `contract.test.ts` regenerates this block and
fails if it does not appear verbatim in this file, so a rail that gains or loses
an operation turns the suite red until the table is regenerated.

`+` supported and exercised · `~` supported, **never run against the provider** ·
`-` not supported, with a reason in the code

<!-- generated by renderRailCapabilityMatrix(); see contract.test.ts -->

| Rail | Provider | Evidence | originate | observe | settle | reverse | probe |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Increase ACH | `increase.ach` | live | ~ | ~ | ~ | ~ | ~ |
| ACH simulator | `achsim.ach` | simulated | + | + | + | + | + |
| Lithic card issuing | `lithic.card` | live | - | + | + | + | + |
| Plaid account linking | `plaid` | live | - | - | - | - | + |
| Base Sepolia, signed here | `base.usdc` | live | + | - | + | - | + |
| Circle Web3 Services, Base Sepolia | `circle.w3s` | live | + | - | + | - | + |

The ACH slot is served by **exactly one** of the first two rows at a time —
`INCREASE_API_KEY` present means Increase, absent means the simulator, the same
rule `createAchRail()` applies. Both are listed here because this is
documentation; `allRailAdapters()` returns only the one actually serving the
slot, because an honesty table for a running deployment must not show a live
rail and its simulator side by side.

### Reading the rows

**The whole Increase row is `~`.** There has never been an `INCREASE_API_KEY` in
this repo. Every wire shape in that adapter comes from `research/ach/NOTES.md`,
where not one line is marked `[MEASURED]`. The code is real and the reasoning
about the settlement promotion is real; none of it has met a bank. That is now
in the type system and on this table, not only in a README paragraph.

**Lithic cannot originate.** A card rail never originates a payment — the
merchant's acquirer does, the network routes, and Lithic tells us afterwards,
twice and for different amounts. `POST /v1/simulate/authorize` exists and is
deliberately **not** exposed as `originate`: it plays the acquirer for a test,
which is the opposite of us instructing a payment.

**Plaid is 1 of 5, and is still in the table.** It moves no money, observes no
money, settles nothing and reverses nothing — `plaid/types.ts` argues at length
that it must never be bent into a `PaymentRail`, and that argument still holds.
What it has is the fifth operation, asked of it exactly as it is asked of
Lithic. A matrix whose most-refused row is the integration everyone assumes is a
payment rail is worth more than a matrix that leaves it out.

**USDC cannot observe or reverse.** Nobody calls us: there is no webhook on this
rail in this deployment, and settlement is read off the chain by asking. And a
confirmed chain transfer is final — no return code, no chargeback, no recall.
`supportsReturns: false` and `returnWindowDays: null` have said so since that
file was written. A `reverted` transaction is a **failed origination**, not a
reversal: the transfer never happened and no USDC moved.

## 4. What the contract deliberately does not do

**It does not unify the instructions.** `initiateCredit(TransferRequest)` and
`send(StablecoinPayoutInstruction)` take different arguments because the rails
are different — an ACH instruction needs a routing number and a SEC-code intent,
a USDC instruction needs a chain id and a token contract. Flattening them into
one union would move the branch from the caller into the adapter and call it an
abstraction. A caller that is originating has already chosen the rail by
choosing the destination. So `OriginatingRail<I>` is **generic in its
instruction and uniform in its outcome**, and the outcome is the half a generic
consumer reads.

**It does not replace `PaymentRail`.** That interface is the right shape for the
rails that have all four of its methods, and both ACH adapters keep it
untouched. The contract is the smaller thing underneath: what survives when you
also have to describe a card rail that cannot originate and a bank-linking
adapter that cannot move a cent.

**It does not re-expose `getTransfer`.** A read-back by provider id is not part
of the intersection of five rails, and a caller that needs one already knows
which rail it is holding.

## 5. The payoff

Two generic things, and both are real. Neither knows which rail it is holding.

### A settlement reporter

```ts
reportSettlements(rails: readonly ObservingRail[], deliveries: readonly RailDelivery[])
  -> { settlements, nonSettling, unroutable, duplicates, net }
```

It routes each verified delivery to the rail whose slug matches, calls
`observe`, and adds up `bigint` minor units per currency. It contains no `if`
about ACH, no `if` about cards, and does not mention either word.

`contract.test.ts` drives a **real** simulated ACH transfer to settlement, takes
the exact signed bytes the simulator produced, puts them in an array next to the
**measured** Lithic payload for the $50.00-authorised / $73.40-cleared fuel pump
from `docs/CARD-CORRECTIONS.md`, and gets `$125.00 + $73.40` out of one call.
The $50.00 authorisation contributes nothing, because a hold is not a movement.

**This was not possible before**, for a concrete reason: the `settled` member of
`RailEvent` carried no amount. `returned` did, `settled` did not, so the only
rail-agnostic thing a consumer could learn from a settlement was that one had
happened. On ACH the missing number is recoverable — a transfer settles for its
face amount — which is why the gap survived. On a card it is not, and
"settlement is not authorisation: different amount, days later" is the whole
track. **`settled` now carries `amount: Money`**, and the two producers were
updated at the same time. That is the one interface change this work made.

### A liveness reporter

```ts
probeRails(rails: readonly RailAdapter[]) -> readonly RailProbe[]
```

Each adapter owns its own cheapest authenticated read; this fans out, keeps
order stable, and **cannot throw** — a rail whose probe rejects is reported
`unreachable` with the error as its detail, because one provider having a bad
afternoon must not take the honesty table down.

`makeRailProbe` is the only constructor for a `RailProbe`, and it computes
`label` itself:

```ts
LIVE  iff  evidence === 'live'  &&  liveness === 'live'
```

**Both halves, every time.** A simulator that is working honestly reports
`liveness: 'live'` — it is in this process, it is running — and is still
labelled `SIMULATED`, because `evidence` is not. A pasted placeholder key
returns 401 and is `SIMULATED` too. The field is not the adapter's to write,
so there is no code path by which a simulator claims LIVE.

### What the settlement reporter found on its first run

It reported **$375.00** of ACH where $125.00 had moved, and the reason is now a
field on `RailSettlement`.

Increase's webhook body is a **pointer**, so `parseEvent` reads the transfer
back, and *every* delivery about that transfer — the submission notification,
the settlement notification, a redelivery three days later — resolves to its
current state. That is a feature: it is exactly what makes out-of-order delivery
harmless. It also means a feed that sums per delivery counts one settlement once
per notification ever sent.

The fix is not deduplication by delivery, because a card transaction settles as
many times as the merchant likes: `auth 1000, clearing 600, clearing 300` is two
settlements on one token, and keying those by the transaction would lose $3.00.

So `RailSettlement.settlementRef` is supplied **by the adapter**, which is the
only thing that knows which kind of rail it is:

| Rail | Settlement identity | Because |
|---|---|---|
| ACH | the **transfer** id | an ACH transfer settles once; every pointer re-read is the same settlement |
| Card | the **clearing event** token | one transaction settles many times; each capture is its own |
| USDC | the **transaction hash** | one hash, one transfer, one confirmation |

`reportSettlements` dedupes on `(provider, settlementRef, kind)` — twice is one,
the same rule the webhook layer applies to deliveries, applied here to money —
and puts the duplicates in their own bucket rather than discarding them, because
a feed that silently drops a second copy is indistinguishable from one that
never received it.

## 6. Known gaps, stated rather than hidden

- **`achRailHealth()` in `achsim/factory.ts` labels the ACH slot `LIVE` from
  `INCREASE_API_KEY` being a non-empty string, with no round trip.** That is
  liveness by presence, which is precisely what `src/lib/integrations/probe.ts`
  was written to stop — "a system ends up labelling four providers LIVE because
  someone pasted the placeholders out of `.env.example`". It is left exactly as
  it was, because changing it would change behaviour and this was a refactor.
  `increaseAchAdapter().probe()` is the version that earns the word.
- **Nothing outside `src/lib/rails/` consumes the contract yet.** The five
  bespoke probes in `integrations/probe.ts` and the card path through
  `src/lib/holds/` are the callers that should collapse onto it, and both are
  owned elsewhere.
- **`parseLithicEvent` and `deriveCardEvents` (in `src/lib/holds/`) both order a
  transaction's events by `created` with payload order as the tie-break.** They
  agree by inspection, not by construction. They map the same payload to
  different targets, and inverting the layering so that `rails/` depended on
  `holds/` would have been worse.
- **`CORRECTION_DEBIT` and `CORRECTION_CREDIT` are not classified.** They are
  published Lithic event types and no sandbox endpoint emits them —
  `/v1/simulate/correction`, `/correction_debit` and `/correction_credit` are
  all 404, measured. They almost certainly move money, and "almost certainly" is
  not the standard, so they come back as `unknown` with `unmodelled_event`:
  a 200, the bytes kept, and the decision left to `rail_event_semantics`.
- **`observe` is declared `false` for Circle even though Circle offers
  subscription webhooks.** This deployment does not use them and has never
  received one.
